# RFC: DBR-005 Usage of Parameter Stores for Runtime Configuration

## Author  
Dat Tran  

## Problem  
We need a flexible and secure way to provide runtime parameters to application containers built in the DevOps pipeline.  

## Proposed Solution  
Use a parameter store to fetch runtime parameters before containers are executed.  

## Details  
- Parameters (e.g., sensitive credentials, environment-specific configs) will be stored securely in a parameter store such as AWS SSM Parameter Store, HashiCorp Vault, or Azure Key Vault.  
- Containers remain parameter-agnostic at build time, with no hardcoded parameters baked into the image.  
- At runtime, a script or application entrypoint will fetch the required parameters from the store and inject them as environment variables or configuration files before the application starts.  

## Alternatives  
1. **Embed parameters into the container image**  
   - Insecure and inflexible, as changes would require rebuilding the container.  

2. **Use a configuration management system to fetch full configurations at runtime**  
   - Suitable for broader application configurations but may introduce complexity if sensitive parameters are handled improperly.  

## Impact  
Medium:  
- Introduces an additional dependency on a parameter store system.  
- Improves security by keeping sensitive data external to containers.  
- Enhances flexibility by enabling dynamic updates to parameters without requiring new builds.  

## Open Questions  
- Which parameter store to standardize on (e.g., AWS SSM vs. Vault)?  
- What access control policies are needed for the parameter store?  

## Timeline  
Adopt immediately for upcoming containerized deployments.
